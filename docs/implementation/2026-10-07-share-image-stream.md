# 공유 이미지 전송 제한

공유 API의 이미지 업로드는 Content-Length가 없거나 실제 크기보다 작으면 전체 본문을 `arrayBuffer()`로 읽은 뒤 5,000,000바이트 제한을 검사했다. 모델·영상 업로드와 달리 이미지의 수신 중단 시점이 제한되지 않았다.

이미지도 스트림을 읽으면서 실제 누적 바이트를 검사한다. 제한을 넘으면 reader를 취소하고 HTTP 413으로 응답하며, 이미지 저장을 시작하지 않는다. 허용된 본문만 합쳐 기존 PNG/JPG/WebP 시그니처 검사와 R2 저장을 수행한다. 전송 중단은 HTTP 400으로 안내하고 이미 저장된 이미지를 덮어쓰지 않는다. 허용 크기와 계정/기존 작성자 키 권한 검사, 발행된 스냅샷의 불변성은 기존 기준을 따른다.

## 검증

- 수정 전 회귀 테스트 3개가 실패했다. 두 초과 스트림은 끝까지 읽혀 취소되지 않았고, 끊긴 전송은 응답 대신 예외를 전파했다.
- 헤더 없음/과소 신고 사례 모두 600,000바이트 청크 20개 중 9개에서 중단·취소·413을 확인했다. 공유 자산은 생성되지 않았다.
- 정확히 5,000,000바이트의 입력을 동일한 바이트로 저장했다. 이어진 전송 실패에서 400과 기존 바이트 보존을 확인했다.
- 관련 공유·계정 테스트 31개 통과. 전체 1,010개 통과/선택 통합 검사 6개 제외. TypeScript와 Vite 빌드 통과.

이는 실제 Request/ReadableStream과 메모리 저장소를 이용한 서버 회귀 검증이다. 실제 Cloudflare 수신 메모리 측정, 운영 업로드, 브라우저 조작 검증으로 확대하지 않는다. 이 변경은 아직 운영 배포하지 않았다. 운영 인증과 최종 화면/연속 인수 검증은 계속 남아 있다.

## 로컬 Worker·R2 후속 검증

`scripts/share-image-stream-native.test.ts`를 운영과 분리된 `127.0.0.1:8815` Wrangler와 별도 로컬 R2 상태에서 실행했다. 명시적 합성 A/B 계정 및 기존 키 각각에서 길이 헤더 없는 12MB 스트림은 HTTP 413, 이어진 발행은 자산 미존재로 409를 반환했다. 정확히 5,000,000바이트인 자체 PNG와 후행 패딩 입력은 204로 저장하고 발행 후 전체 바이트가 동일하게 조회됐다. 공유 3개를 모두 회수했으며 스냅샷과 이미지 요청 모두 410을 확인했다. 테스트 Worker는 종료했다.

후속 [원본 결과](../validation/2026-10-07-share-image-stream-native.json)는 실제 로컬 HTTP/R2 결과다. 실제 Supabase 인증, 브라우저 이미지 렌더, 운영 업로드 및 전체 수신 메모리를 검증한 것은 아니다. 600KB 청크 9개에서의 읽기 취소는 앞선 Request 스트림 회귀 근거이며 HTTP 클라이언트의 네트워크 송신량으로 확대하지 않는다.

후속 통합 검사 1개를 실제 Worker에서 통과한 뒤 기본 전체 테스트도 다시 실행했다. 1,010개 통과/선택 통합 검사 7개 제외다. 제외 수 증가는 새로 등록한 명시적 로컬 Worker 검사이며, 이 검사는 위 실행에서 별도로 통과했다.
