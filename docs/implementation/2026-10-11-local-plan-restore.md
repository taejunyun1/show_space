# 저장·재열기와 복원 중 자동 저장 보호

2026-10-11. 원문 1 §24–26/40 및 2 §70의 저장·복원 흐름을 보완했다. 앞선 두 JPEG 도면 전시를 실제 프로젝트 목록으로 왕복하고 저장소를 다시 연결해 도면/Scene 자산을 확인했다.

## 발견한 문제

- 전시 A의 자동 저장이 남은 상태에서 저장된 B를 열면 늦은 A 저장이 로컬 ‘마지막 프로젝트’를 다시 A로 선택했다. 화면은 B지만 다음 시작에서 A를 열 수 있었다. 아직 저장하지 않은 가져오기 전시의 지연 저장에서도 재현됐다.
- 같은 ID의 저장된 버전을 복원해도 이전 편집의 자동 저장 큐가 남았다. 실행하지 않은 옛 저장이 복원 후 인정된 최신 revision을 사용해 복원 내용을 덮어쓸 수 있었다. 실행 중 옛 저장의 revision 충돌도 새 복원 화면에 실패로 표시됐다.
- 초기 불러오기 응답이 늦으면 새 편집을 ‘저장됨’으로 바꾸거나 직접 복원/더 최신 불러오기의 상태·안내를 옛 오류로 덮어썼다.

## 바꾼 동작

기본 자동 저장 writer는 현재 전시 ID를 확인하는 활성화 조건을 전달한다. IndexedDB `save`는 비동기 revision 조회 뒤, 같은 원자적 transaction 안에서 조건을 다시 검사한다. 다른 전시로 이동한 경우 옛 문서는 계속 저장하되 시작 프로젝트를 바꾸지 않는다. 새로 가져온 현재 전시는 정상 저장 후 시작 프로젝트로 선택된다. 기존 CAS revision·보관/용량 오류 제한을 유지한다.

이미 저장된 프로젝트를 복원하면 해당 ID의 이전 대기/예약 큐를 폐기한다. 이미 실행 중인 옛 transaction은 기존 CAS로 보호하고, 복원 뒤 도착한 옛 실패/완료로 새 상태를 바꾸지 않는다. 다른 ID에 남은 편집은 폐기하지 않고 비활성 저장한다. 복원 후 새 편집은 정상적으로 다시 저장한다.

불러오기는 요청 순번과 시작 `projectContextVersion`으로 결과·오류의 소유권을 검사한다. 새 불러오기나 같은 ID의 문서 복원 뒤 옛 결과는 적용하지 않는다. 일반 편집으로 문서가 달라졌다면 편집과 기존 저장 상태를 유지하면서 초기화만 끝내고 자동 저장을 이어 간다.

## 검증한 작업 흐름

기본 writer·store·프로젝트 저장 함수를 실제로 실행했다. IndexedDB API는 `fake-indexeddb`가 구현하며 임의 함수 응답만 반환하는 저장 mock으로 대체하지 않았다. 지연 위치는 writer가 시작하기 전과 실제 IndexedDB revision 요청 성공 직후를 모두 포함한다. 같은 ID 복원은 실제 CAS 저장 후 큐 두 개/실행 중 실패까지 확인했다. 새 입력·현재 복원 뒤 새 편집·초기 불러오기 중 편집의 정상 경로도 유지된다.

실제 React/jsdom `ProjectsDialog`에서 두 도면 전시의 최신 이름·바닥색·비공개 메모를 저장하고 다른 전시로 열기→원래 전시 다시 열기를 수행했다. 같은 저장소에 새 연결을 만들고 기본 `hydrateEditor`로 전체 문서를 복원했다. 재열기 revision은 2이며 초기화만으로 증가하지 않았다. 실제 `PlanView`에서 A/B Scene을 복원해 각자의 벽, 원본, 축척 및 SVG 도면 이미지 참조를 확인했다. A는 1000×800/10mm·보정, B는 800×1000/9.95mm·미보정이라는 저장 상태를 그대로 유지한다. 최신 비공개 메모를 보존하고 최종 저장 revision 3 및 ZIP 정확 복원을 확인했다.

ZIP의 PNG 자산 2개는 Scene 이미지 SHA와 일치하고 별도 Python ZIP 검사에서도 CRC 오류가 없다. 이번 검증은 실제 브라우저 이미지 디코딩·픽셀 비교가 아니라 저장된 원본 바이트와 DOM 이미지 참조의 일치다. [작업/백업 자료](../validation/local-plan-restore-2026-10-11/), [검증 기록](../validation/2026-10-11-local-plan-restore.json).

임시 최종 소스 복사본에서 제품 3파일만 이전 main `a32986aa4856ccee5276f35d362bfdf54dacf50f`로 교체했다. 같은 최종 12개는 **8 실패/4 통과**, 수정 후 전부 통과다. 대상 8파일/114개, 전체 **1,558개 통과·선택 10 제외**, TypeScript·production build 통과다. 테스트의 메모 입력은 실제 `patchNote` 인터페이스에 맞췄다. 초기 잘못된 테스트 타입을 제품 오류로 집계하지 않는다. 기존 큰 청크 안내는 남는다.
