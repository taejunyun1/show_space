# 작품 이미지 자동 해상도와 메모리 배분

전체 구현 목표의 성능 기반 작업이다. 도면 인식/문·설비 범위를 확장하지 않는다.

## 구현

- 렌더링 전용 Canvas 파생본을 사용한다. 이미지 URL, 작품 실제 크기, 원본 프로젝트, Scene, JSON/자산 백업/GLB/PDF 출력의 자산 경로를 바꾸지 않는다. 예제 이미지 묶음은 개별 패널을 먼저 잘라 파생본을 만들어 선명도를 유지한다.
- 화면 밖은 128px, 화면 안은 512px 기본으로 표시한다. 선택/화면에서 차지하는 픽셀 수에 따라 1024/2048px로 올라간다. 500개 등 많은 작품은 기본 해상도도 줄인다. 동일 이미지/패널은 공유하고, 보수적인 정사각 RGBA+mip 산정으로 Canvas별 작품 목표 예산 192MiB를 배분한다.
- 작은 시점 변화에는 해상도를 유지한다. 다른 작품을 높이기 전에 기존 고해상도 작품을 낮추고, 실제 material에 새 이미지가 붙을 때 이전 texture를 해제한다. 읽기 작업은 최대 4개이며 시작 전 취소된 파생본 요청을 제거한다.
- PNG 캡처의 실제 출력 배율을 사용해 필요한 해상도를 다시 계산하고, 이미지/조명 준비를 기다린다. 캡처 이후 편집 배분으로 돌아간다. 공유 3D 수신 화면도 같은 배분기를 사용한다.

## 확인된 증거

- 전체 테스트 822개 통과, 선택 벤치마크 2개 제외. TypeScript/Vite 빌드 통과. 새 테스트는 100/500 작품 예산, 선택 우선, 같은 자산 공유, 화면 밖, 해상도 유지 구간, 패널 파생 크기, 먼저 낮춘 뒤 올리기, 해상도별 수명, 대기 요청 취소를 다룬다.
- 실제 개발 전용 장면에 50벽, 서로 다른 2048px 이미지 100개, 10 Spot/10 Area를 넣었다. 신규 렌더러 전체 시점은 작품 모두 512px, map 추정 133.33MiB/GPU texture 104개, 준비 완료이다. 2048 정사각 이미지 100개의 RGBA+mip 이론값은 약 2133MiB이며 이는 실측 이전 VRAM 값이 아니다.
- 근접 선택 시 98개 128px/1개 512px/선택 1개 2048px, map 추정 30.83MiB. 미리보기/캡처 시 근접 두 번째 작품 1024px, 34.83MiB. 실제 캡처 관측은 4 shadow casters, DPR1.75, LOD 준비 완료였고 1920×1080 PNG를 저장·검사했다.
- 일반 편집기에서 예제 작품 이미지와 액자/측정/시점 표시가 정상이며 콘솔 경고/오류 없다. 개발 검증 경로/문구/번들은 production 빌드에 포함되지 않는다. 상세 수치와 화면은 ../validation/2026-10-04-artwork-texture-lod.json 참고.

## 미완료인 전체 성능/인수 조건

이 예산은 작품 이미지 배분이며 전체 GPU VRAM 한도를 보장하지 않는다. 벽·바닥 텍스처/환경/그림자/프레임버퍼/GLB의 이미지와 교체 순간의 겹침, CPU 이미지 디코딩 메모리는 별도다. 다중 Canvas도 별도 예산을 갖는다. 삼각형 100만 장면, 사용자 SketchUp 모델, 모바일 실기기, 입력 응답 p95 및 실사용자 5명, 실제 로그인/두 계정·기기, 전체 24단계 인수는 미완료다. SharedViewer 연결은 빌드/기존 테스트로 확인했으며 이번 단계의 실제 신규 공유 수신 왕복은 미검증이다. 최종 목표는 계속 진행한다.

같은 렌더러에서 전체→근접→전체를 실제 컨트롤로 반복한 후 100개 512px/map133.33MiB/GPU texture104개/LOD 준비 완료로 복원됨을 확인했다. 개발 중 hot reload의 자원 잔여 수치를 생산 결과로 사용하지 않는다.

Cloudflare `988c8b9d-0e3b-47a5-89fd-c8cd3519cdb1` 배포, 공개 entry `/assets/index-BlUsTePV.js`·작품 정상 표시·품질 선택·경고/오류 0 확인. 기존 설정/D1/R2 바인딩을 keep-vars로 보존하고 공개 프로젝트나 공유 자산에 합성 장면을 입력하지 않았다.
