# 클라우드 저장 화면의 취소·재시도와 전환 보호

2026-10-11. 직전 저장 큐 보호를 실제 `CloudProjectsPanel` 버튼·목록·체크박스·부모 busy 상태에 연결했다. 도면 인식·유료 기능 범위는 늘리지 않는다.

## 수정한 화면 동작

로그인 세션을 기다리는 동안 전시가 바뀌면 ‘현재 프로젝트 저장’이 새 전시를 저장할 수 있었다. 계정/전시 A→B→A 전환과 같은 ID의 복원, 취소·unmount 뒤 옛 응답도 새 화면의 오류·진행 상태를 바꿀 수 있었다. 취소 버튼은 요청을 abort했지만 응답이 끝날 때까지 화면을 잠갔고, 실제 cloud status가 `saving`이면 저장 버튼도 계속 잠겼다.

- 화면은 계정 ID·프로젝트 ID/복원 context의 변화를 동기적으로 구독해 요청과 도면 연결 정보를 폐기한다. 빠른 A→B→A도 epoch가 달라진다. 새 요청은 이 범위와 controller를 소유하며, 옛 결과/오류/완료가 새 요청의 busy를 해제하지 않는다. React 렌더 전 두 버튼 클릭도 한 요청만 시작한다.
- 취소는 원래 요청의 계정·전시를 대상으로 실행하며 즉시 컨트롤을 해제한다. cloud queue도 진행 중 상태를 재시도 대기로 바꾸고 원본 파일을 유지한다. 계정이 바뀐 뒤 새 계정의 작업을 대신 취소하지 않는다. 화면 해제 때 부모 busy도 풀어 오류 복구 이후 프로젝트 목록이 잠기지 않도록 했다.
- 연결·자동 저장 체크박스의 지연 조회는 같은 epoch에서만 적용한다. 옛 연결이나 오류가 복원된 화면에 나타나지 않는다.
- 클라우드 파일 열기와 충돌 복사본 만들기는 이동/회전 및 시작 문서의 최신 편집을 검사한다. 늦은 파일 읽기나 복사 저장 중 새 편집을 버리지 않는다. 준비된 새 복사본은 비활성으로 저장한 뒤 검사된 활성화를 거친다. `openEditableCloudProject`도 마지막 로컬 읽기/활성화에 guard를 전달한다.

## 검증한 UI와 저장 작업

실제 React/jsdom StrictMode UI에서 세션/파일/저장 응답을 지연시켜 전시 변경, 같은 ID 복원, 전시·계정 왕복, 취소 후 새 요청, unmount, 지연 연결 조회, 읽는 중 편집, 이동 중 열기, 저장 중 복사본 변경 및 두 버튼 동시 클릭을 재현했다. 정상 저장과 다시 시도한 정상 열기도 통과했다. scope 사례의 cloud client/세션/동기화 응답은 adapter이고 실제 IndexedDB API 저장은 fake-indexeddb를 쓴다.

별도 실제 저장 사례는 앞선 두 JPEG/Scene 백업을 입력으로 동일 화면의 버튼을 조작한다. `exportProjectBackup`의 실제 native 이미지 decoder·기본 로컬/cloud writer·client·production Worker handler를 실행한다. Worker는 SQLite·메모리 R2·합성 인증 fixture다.

1. ‘현재 프로젝트 클라우드 저장’으로 실제 ZIP을 보냈다. Worker가 **201/revision 1**을 확정한 뒤 응답을 지연시켰다.
2. ‘클라우드 작업 취소’ 직후 대기 상태와 활성화된 저장 버튼을 확인하고 즉시 재시도했다. 옛 응답이 돌아와도 새 요청은 진행 중 상태를 유지했다. 대기 ZIP은 바이트가 같다.
3. 같은 원본 재시도는 기존 Worker의 동일 파일 처리로 **200/revision 1**을 반환했다. 새 버전을 중복 생성하지 않고 대기 파일을 해제했다. 저장됨·연결 체크박스·목록 새로고침 callback을 확인했다.
4. 실제 자동 저장 체크박스로 일시 정지했다. Scene A를 복원한 뒤 수동 저장하면 **remote/local revision 2**와 완료 상태가 되며 자동 저장은 계속 false다. 원본 Scene 2개와 비공개 메모를 유지한다.
5. private API로 파일을 다시 읽어 실제 ZIP import가 현재 프로젝트 전체와 일치함을 확인했다. 최신 R2 파일 1개이며 PNG 2개는 이전 Scene 이미지 SHA와 같고 별도 Python CRC 검사도 통과했다.

지연 transport는 abort 뒤에도 서버가 받아 둔 응답을 반환하도록 한다. 이 검증은 실제 브라우저 fetch 취소를 주장하지 않고, 응답 이후 소유권 보호까지 실행한다. [수신 백업](../validation/cloud-panel-2026-10-11/project.gonggan.zip), [버튼/API 기록](../validation/cloud-panel-2026-10-11/workflow.json), [검증 기록](../validation/2026-10-11-cloud-panel-workflow.json).

추가 실제 로컬 활성화 사례는 cloud package 검증·새 로컬 복사본 저장 뒤, IndexedDB의 마지막 활성화 조회 성공 이벤트에서 편집을 넣었다. guard가 transaction을 취소하고 원래 시작 프로젝트와 최신 편집을 유지한다. 저장된 복사본은 비활성으로 남는다. 정상 사례는 원본과 독립적인 새 ID로 열고 cloud 연결도 유지한다.

임시 최종 소스 복사본의 제품 3파일만 이전 main `b5eb634fc2e6cf8ac5fa27abab64d02b80275336`로 바꾸면 같은 최종 15개는 **13 실패/2 통과**, 수정 후 모두 통과다. 작업 체크아웃은 되돌리지 않았다. 새 회귀 15개, 대상 8파일/74개 및 전체 **1,580개 통과·선택 10 제외**, TypeScript·production build 통과다. 기존 큰 청크 안내는 남는다.

실제 브라우저 렌더·fetch/Abort·저장/새로고침, 운영 인증/두 계정·기기·공유 URL, GPU/3D 캡처, 실제 사용자 도면·모델/SketchUp, 성능/성공 지표 및 원문 24단계 전체 인수는 미완료다. 이번 변경은 즉시 재배포하지 않는다. 다음은 계정 복원 지점의 준비·저장·열기와 같은 화면 범위 보호를 점검한다. 기존 도면 초안·문/설비 후보 범위와 독립 설비 편집·유료 생성 기능 유보는 유지한다.
