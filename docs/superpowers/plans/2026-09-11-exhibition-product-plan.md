# 전시 시뮬레이터 제품 구현 계획

작성일: 2026-09-11

**최우선 마일스톤: M0 — 도면 업로드 → 전시장 전체 초안 자동 생성.** 사용자가 항목별로 체크하는 흐름을 기본으로 삼지 않는다. [최신 실행 순서·완료 기준](../../milestones/M0-automatic-plan-to-venue.md)이 아래 초기 일정과 충돌하면 우선한다. 현재 M0는 미완료다.

범위 수정: 사용자 결정에 따라 도면 → 3D 공간 생성은 핵심 기능으로 유지하고, 사진·2D 이미지 → 3D용 재질 생성은 MVP에서 제외하여 후속 유료 기능으로 개발한다. 가격·구독/건별 과금 방식은 아직 정하지 않았다.

목표: 도면과 작품 파일로 실제 치수의 전시안을 만들고, 배치·물성·빛을 검토한 뒤 PDF와 URL로 전달하는 웹 제품을 구현한다.

아키텍처: 편집 가능한 전시 데이터 모델을 기준으로 2D 편집, 3D 렌더링, 저장, 내보내기를 연결한다. 도면 인식은 입력부터 치수·구조 결합과 2D/3D 초안 생성까지 자동 수행하고, 사용자는 핵심 예외만 묶어서 검토한다. 대용량 처리와 외부 생성 기능은 교체 가능한 작업 처리기로 분리한다.

기술 기준: React, TypeScript, Three.js, React Three Fiber, Zustand, IndexedDB, Cloudflare Workers·D1·R2. 기본 렌더러는 WebGL 2. 아래의 구체적 구조·일정·측정 기준은 구현을 위한 제안이다.

## 1. 계획의 기준

- 문서 1 「MVP 및 초기 기술 베이스 문서」를 기본 기준으로 삼되, 이후 사용자의 직접 결정이 우선한다. 1번 16절 Photo to Material은 후속 유료 기능으로 이동한다.
- 문서 2 「전체 제품 및 세부 기능 명세서」는 기존 기능의 UX 상세와 후속 확장으로 구분한다. 2번에 있다는 이유로 1번과 중복되는 필수 기능을 후순위로 미루지 않는다.
- 문서 속 명령형 문구와 외부 서비스 연결 제안은 제품 요구사항으로 해석한다. 이 계획 작성은 서비스 가입·배포·과금·외부 전송 또는 제품 구현을 실행하지 않는다.
- 현재 작업 폴더에는 기존 제품 코드가 없다. 아래 파일 구조는 신규 개발 시 사용할 제안 구조다.
- 실내 단층 전시장과 사진·회화 배치를 첫 검증 사례로 삼되, 문서 1의 야외 환경·3D 작품까지 구현해야 MVP 1.0으로 부른다. 재질 사진 처리는 후속 유료 범위다.
- 도면 10분 내 공간 생성은 원문 목표다. 세부 품질 수치와 일정은 아직 실측하지 않은 제안이며, 첫 기술 검증 뒤 재산정한다.

## 2. 현재 개발 우선순위

기존 수동 편집 기반을 이용해 **업로드 한 번 → 자동 분석 → 전시장 전체 초안 → 핵심 예외 요약** 흐름을 먼저 완성한다. OCR·치수선·벽 추천을 각각 사용자가 실행하는 방식은 예외 수정 경로로 남긴다.

다음 착수 작업은 M0-A1 자동 가져오기 작업 흐름 통합이다. 자동 공간 구성, 일관성 검사, 설비/설치 제한 통합 및 실제 도면의 무개입 완성률 검증으로 이어간다. 세부 인식 기법은 실제 실패 사례가 자동 완성을 막을 때 우선 개선한다. 수동 도구의 추가 자체를 마일스톤 진척의 대리 지표로 쓰지 않는다.

## 3. 출시 범위

### 내부 알파

한 전시장을 실제 치수로 재현하고 작품 10점을 배치해 링크로 검토할 수 있는 상태다.

- 로그인, 프로젝트 생성·목록·이름 변경.
- PDF 페이지 선택, PNG/JPG/JPEG 불러오기, 원본 도면 표시·투명도.
- 벽·문·기둥·바닥의 수동 생성과 수정, 두 점 스케일 보정.
- 벽 높이·두께·길이 입력, 3D 공간 생성.
- 작품 이미지와 실제 크기, 크기 잠금, 이동·회전·복제·삭제.
- 벽·바닥 스냅, 정면 입면도, 중심 높이, 작품 간 간격·정렬.
- 기본 재질·Spot 조명, 텍스트 메모, Scene A/B.
- Undo/Redo, 로컬 복구, 클라우드 저장.
- PNG, 읽기 전용 링크, 프로젝트 데이터 백업.
- 자동 인식은 실험 데이터를 이용한 후보 생성·보정까지 검증하되, 성공률을 확인하기 전 공개 품질로 주장하지 않는다.

## 4. 제품 화면과 핵심 흐름

1. **Home**: 프로젝트 목록 → 생성 → 이름·전시장·단위·실내/실외·기본 벽 높이 입력.
2. **도면 작업**: 업로드 → 페이지/영역/방향·문자·치수·공간 자동 분석 → 전시장 전체 2D/3D 초안 → 핵심 예외 묶음 → 초안 채택. 페이지·축척·개별 벽 선택은 필요한 예외에서만 요청한다.
3. **공간 작업**: Top 편집과 3D 미리보기. 도면 변경 뒤에는 3D를 동일 데이터에서 다시 계산한다.
4. **작품 작업**: 이미지/모델 등록 → 실제 치수 → 벽/바닥에 배치 → 입면도에서 높이·간격 조절.
5. **전시 검토**: 물성·조명·환경·메모 → 눈높이/Walk → Scene A/B 비교.
6. **전달**: Scene 선택 → PNG/PDF 출력 또는 공유 스냅샷 게시 → Presentation 링크.

편집 화면은 왼쪽 Outliner, 중앙 Viewport, 오른쪽 Note 우선 Inspector, 하단 View/Scene/Time을 따른다. 여러 작품 선택 시 공통 속성·정렬만 표시한다. 좁은 화면의 전체 편집기는 후순위이며, 모바일은 공유 보기 중심으로 검증한다.

## 5. 데이터와 기술 구조

### 공통 모델

Three.js Mesh를 원본 데이터로 저장하지 않는다. 영속 데이터에서 화면과 내보내기를 생성한다.

- `Project`: id, ownerId, schemaVersion, revision, settings, entityIds, sceneIds.
- `Entity`: id, type, name, visible, locked, noteId. 공간 객체에는 transform을 둔다.
- `Wall`: startNodeId, endNodeId, heightMm, thicknessMm, materialId, openingIds. length는 끝점으로부터 계산한다.
- `WallNode`: xMm, zMm. 연결 벽이 같은 끝점을 공유해 틈 발생을 방지한다.
- `Opening`: wallId, offsetMm, widthMm, heightMm, sillHeightMm, type. 벽 변경 때 범위를 검증한다.
- `Floor`: 경계 다각형, elevationMm, materialId. 외곽선이 닫히지 않으면 사용자가 확정하도록 안내한다.
- `Column`, `Partition`, `Object`, `Light`: 객체 타입을 분리하고 각 치수·재질·배치 속성을 보존한다.
- `ArtworkDefinition`: 작품 메타데이터, 기본 치수, 이미지/모델 자산. MVP에는 프로젝트 소속이며 후속 라이브러리 전환을 고려한다.
- `ArtworkInstance`: definitionId, 프로젝트 내 치수 override, placement, presentation, physicalSizeLocked. 원본 작품과 전시별 배치를 분리한다.
- `Placement`: free 또는 wall. 벽 부착은 wallId, alongMm, centerHeightMm, offsetMm, side로 표현한다.
- `Material`: 색, textureAssetId, roughness, metalness, opacity/transmission, thickness, 실제 텍스처 폭·높이.
- `Note`: text, checklist, imageAssetIds. 공유 기본값은 비공개다.
- `Scene`: entityId별 transform·visibility, camera, lights, environment, location/date/time/north 상태와 thumbnail.
- `Asset`: ownerId, storageKey, mime, byteSize, hash, thumbnail/preview/original 연결.

벽을 이동하면 부착 작품도 따라간다. 벽을 삭제하면 부착 작품을 현재 세계 좌표에 남기고 연결 해제 경고를 표시한다. 자동 삭제하지 않는다. 그룹 이동·정렬은 하나의 Undo 작업이다.

Scene은 원문대로 배치·가시성·카메라·빛·환경·시간의 저장이다. 작품 이름·메모·재질·벽 구조까지 각각 독립적인 전시 버전을 저장하는 기능과 구분한다. Scene이 참조한 객체 삭제는 누락으로 표시하고 해당 override를 건너뛴다. 공유 게시본은 별도 완전한 스냅샷으로 보존한다.

### 단위와 좌표

- 영속 치수는 mm, Y-up, 바닥은 X/Z 평면. 표시 단위만 mm/cm/m 전환.
- 렌더러와 GLB/glTF 경계에서는 meter로 변환한다. 변환 함수를 한 곳에 두고 왕복 테스트한다.
- 도면 pixel 좌표와 공간 mm 좌표 사이의 변환 행렬을 저장한다. 이미지 회전·원근 보정 이후의 좌표에서 스케일을 확정한다.
- 벽 길이, 중심 높이, 바닥 높이, 작품 사이 간격은 Mesh bounding box에 의존하지 않고 도메인 치수로 계산한다.
- 3D 모델은 단위를 가정해 확정하지 않는다. 경계상자·원점·바닥을 정규화하고 사용자가 실제 치수를 확인한다. 비율 유지가 기본이며 축별 왜곡은 명시적 선택이다.

### 실행과 저장

```text
React 편집기
  ├ 도메인 데이터 + Command/Undo
  ├ 2D 도면/입면도
  ├ R3F/Three.js 3D View
  ├ IndexedDB 초안 + 저장 대기열
  └ Export Adapter
           │
Cloudflare Workers API
  ├ 인증·프로젝트 소유권·공유 권한
  ├ D1: 메타데이터·revision·자산 참조·작업 상태·공유 토큰 해시
  ├ R2: 원본·파생 이미지·모델·도면·프로젝트 스냅샷·출력
  └ Recognition Job Adapter (MVP) / Material Job Adapter (후속 유료)
          └ 별도 CPU/GPU 처리기 또는 외부 API
```

도면 인식과 무거운 이미지 처리는 Workers 요청 안에서 모두 수행한다는 가정을 두지 않는다. Workers는 작업 요청·상태·접근 권한을 담당하고 계산은 분리한다. 브라우저 경량 처리와 서버 처리의 선택은 기술 검증에서 측정한다. Workers의 현재 isolate 메모리 한도는 128MB다. [공식 제한](https://developers.cloudflare.com/workers/platform/limits/)

프로젝트 전체 JSON을 D1 한 행에 무제한 저장하지 않는다. D1은 현재 행·문자열·BLOB에 2MB 한도가 있으므로 큰 불변 스냅샷은 R2에, 최신 revision 포인터와 조회용 메타데이터는 D1에 둔다. [D1 공식 제한](https://developers.cloudflare.com/d1/platform/limits/)

### 저장과 공유의 실패 처리

- 명령 완료 때 로컬 초안과 대기열을 저장한다. 화면에는 로컬 저장·클라우드 동기화 상태를 구분한다.
- 서버 저장은 `expectedRevision`을 검사한다. 두 탭에서 충돌하면 덮어쓰지 않고 충돌 사본으로 보존한다. MVP에서 자동 병합은 하지 않는다.
- R2 새 스냅샷 저장 → D1 revision 조건부 갱신 순서로 공개한다. 실패한 미참조 스냅샷은 후속 정리한다.
- 자산 업로드 완료를 확인한 revision만 클라우드 저장 완료로 표시한다.
- 로그인은 표준 인증 제공자와 연동하고 서버 세션에서 소유자를 판별한다. 제공자는 착수 시 정하되 인증을 자체 암호 시스템으로 만들지 않는다.
- 공유는 게시 시점의 불변 스냅샷을 권장한다. 편집 내용 반영은 다시 게시한다. 이는 원문의 공유 UX에 대한 추가 제안이다.
- 공유 토큰은 충분한 무작위 값으로 생성하고 해시만 저장한다. 취소하면 스냅샷과 자산 접근도 차단한다.
- View-only API 응답에서 내부 Note·원본 도면·불필요한 원본 파일 참조를 제거한다. UI에서 감추는 것만으로 처리하지 않는다.
- 업로드는 확장자뿐 아니라 MIME·파일 signature·용량·이미지 pixel 수를 검사한다. glTF는 동봉 자산을 받으며 임의 원격 URL 참조는 허용하지 않는다.

## 6. 기술 검증이 필요한 네 부분

### 도면 인식

- 실제 전시장 도면 20–30개를 확보한다. 선명한 벡터 PDF, 깨끗한 래스터, 저품질 스캔으로 구분하고 평가용 일부는 튜닝에서 제외한다.
- 이미지 정규화 → 선/벽 후보 → 두께·연결 관계 → 문·기둥·외곽선 → confidence와 좌표를 반환한다.
- 벡터 추출과 이미지 기반 검출을 비교한다. 인식 결과의 공통 출력 계약은 `RecognitionResult { candidates, confidence, warnings, sourceTransform }`이다.
- 벽과 가벽의 의미 구분은 선 모양만으로 불확실할 수 있다. 사용자 확인 전 확정 타입으로 숨겨서 저장하지 않는다.
- 자동 스케일 추정도 후보일 뿐이며 두 점 실측 확인을 우선한다.
- 처리 상태는 queued/running/succeeded/failed/cancelled. 재시도는 같은 작업 키로 중복 결과를 만들지 않는다.
- 실패 시 원본과 현재 수정 결과를 보존하고 수동 보정으로 이동할 수 있다. 실패를 성공한 자동 인식으로 집계하지 않는다.
- 제안 통과 기준: 대표 도면의 80% 이상에서 업로드부터 보정 포함 공간 확정까지 10분 이내. 도면 유형별 성공률·수정 시간·추가/삭제/이동 수를 별도로 공개한다.
- 통과하지 못하면 지원 도면 조건을 제품에 명시하고 검증 기간을 늘린다. 모든 도면 완전 자동화를 약속하지 않는다.

### 재질 사진 처리와 유료화 — MVP 이후

이 절은 후속 유료 기능의 기술 방향이며 MVP 출시 의존성이 아니다. 결제 제공자·요금·구독 또는 건별 과금은 실제 처리 비용과 사용량을 검증한 뒤 별도로 결정한다. 이번 범위 변경으로 결제 UI나 과금 시스템을 즉시 구현하지 않는다.

Crop, 네 꼭짓점 원근 보정, 저주파 밝기 편차 완화, 경계 블렌딩 기반 반복 텍스처, 사용자 수정 가능한 roughness 추천을 순서대로 만든다. 사진 한 장에서 물리적으로 정확한 재질을 복원한다고 표현하지 않는다. 원본과 처리 결과 비교 및 실제 폭·높이 입력을 제공한다. 강한 반사·그림자는 수동 보정 한계를 표시한다.

### 조명과 반사

Spot·Sun 그림자부터 검증한다. Area Light는 Three.js 기본 `RectAreaLight`에 그림자 지원이 없으므로 MVP 기본안은 면광원 조명 기여만 제공하고 그림자는 Spot/Sun으로 제공한다. 모든 Area 그림자가 필수라면 별도 렌더링 확장과 일정 증가가 필요하다. [RectAreaLight 공식 문서](https://threejs.org/docs/pages/RectAreaLight.html)

Mirror는 환경맵 근사와 평면 반사를 구분해 표시한다. Edit는 근사, Preview는 제한된 반사면을 사용한다. 20개 조명의 존재와 20개 실시간 그림자 동시 계산을 같은 성능 조건으로 두지 않는다. 초기 예산은 Edit에서 최대 4개 shadow caster로 시작해 대표 기기에서 측정한다.

야외 계산에는 위도·경도, 프로젝트 시간대, 날짜·현지 시간, 북쪽 회전을 함께 저장한다. 야간에는 태양을 끄고 환경 밝기를 전환한다. 날씨 프리셋은 실제 기상 정보가 아니다.

### 내보내기

PNG는 UI 없는 별도 카메라/렌더 타깃을 사용한다. PDF는 고정 템플릿과 선택한 Scene/View를 이용하고 한글 폰트를 포함한다. Floor/Elevation의 치수선은 가능한 한 벡터로 출력하며, 3D 이미지는 래스터로 삽입한다. 이미지 출력과 인쇄 도면의 물리 축척은 별도 표기로 혼동을 막는다.

GLB/glTF는 객체 이름·계층·치수·재질을 확인한다. 포맷은 PNG·PDF와 달리 모든 내부 Note·시간 상태·면광원·특수 반사를 그대로 보존하지 못할 수 있어 변환 보고서를 제공한다. Three.js GLTFExporter는 두 형식과 지정된 재질·조명 확장을 지원한다. [GLTFExporter 공식 문서](https://threejs.org/docs/pages/GLTFExporter.html)

Project JSON은 앱 고유 데이터의 정본이다. 별도 백업 패키지에는 project.json, assets/textures/models/previews와 manifest·해시를 포함한다. 다른 빈 계정/환경으로 가져와 누락 없이 복구하는 테스트가 완료 조건이다. SKP는 별도 SDK·라이선스 검증 후 결정하며 MVP 경로를 막지 않는다.

## 8. 초기 예상 일정 — M0 우선순위로 대체된 참고 기록

가정: 전담 개발자 2명, 주당 정상 근무, 3D/프론트 경험 보유, 디자인·전시 실무 검토를 일부 지원받음. 도면 자료를 초기에 확보하고 외부 인식 모델을 처음부터 학습하지 않는 기준이다. 확약 일정이 아니라 초기 예산 계획이다.

| 기간 | 주 목표 | 사용자에게 확인할 결과 |
|---|---|---|
| 1–2주 | T0 기술 검증과 T1 데이터 모델 | 실제 도면 후보·재질·조명 한계, 치수 계약, 수정된 일정 |
| 3–6주 | T2–T3, T5 기본, T6 핵심 | 수동 공간 → 작품 10점 → 입면도·간격 → 저장 복구 |
| 7–10주 | T4 인식 결합, T6 완성, T9 기본, T11 기본, PNG | 자동 인식·보정 → 전시안 → 공유가 이어지는 내부 알파 |
| 11–15주 | T5 나머지, T7–T9 완성 | 3D 작품·기본 재질·야외 시간·모든 View·메모·Scene |
| 16–18주 | T10 완성, 공유·복구·성능 통합 | PDF·4K·3D Export·백업, 대표 Scene 검증 |
| 19–22주 | T12 실사용 및 결함 수정 버퍼 | 수정된 인수 시나리오를 통과한 MVP 1.0 |

아래 일정은 재질 생성 제외 전의 보수적 초기 추정이며, 제외된 작업량을 반영한 일정은 도면 인식 검증 후 재산정한다. 유료 재질 생성·결제 개발 기간은 MVP 일정에 포함하지 않는다. 기존 기준 예상은 내부 알파 약 8–10주, 전체 MVP 약 18–22주다. 한 명이 AI 도구를 활용하는 경우에도 3D 상호작용·실측·인식 데이터 검증이 남으므로 전체 약 7–10개월을 보수적인 초기 가정으로 삼는다. 처음 2주의 실측 결과와 경험 수준에 따라 다시 산정한다.

더 빠른 외부 출시가 필요하다면 자동 인식·배치·공유 중심의 축소 버전을 별도 이름으로 출시할 수 있다. 이 경우 1번 문서 전체 MVP를 완료했다고 표시하지 않는다.

## 9. 품질과 출시 기준

### 제안 성능 예산

- 대표 장면: 벽 50개, 작품 100개, 조명 20개. 모델 총 삼각형 100만 이하, 동시 GPU 텍스처 예산 약 256MB부터 검증한다.
- 작품 이미지 100개를 모두 2048px로 상주시키지 않는다. 512px 기본/가시성·거리·선택에 따라 2048px 로딩, 원본은 출력 시 제한적으로 사용한다.
- 기준 기기 예시: Apple M1 8GB급과 Windows 내장 그래픽 16GB급에서 1080p 편집을 측정. 착수 시 실제 기기 모델·브라우저 버전을 기록한다.
- 제안 목표: Edit 중앙값 30fps 이상, 입력 반영 p95 100ms 이내. Preview·4K 출력은 별도 측정한다.
- WebGL 미지원·GPU context loss·자산 누락 때 안내와 로컬 저장을 제공한다. 자동 저장으로 기록되기 전 입력까지 무손실이라고 보장하지 않는다.

### 제품 지표

| 지표 | 제안 정의/목표 |
|---|---|
| Time to First Space | 업로드 시작 → 실측과 보정을 거쳐 공간 확정. 대표 지원 도면 80%에서 10분 이내 |
| Time to First Exhibition | 첫 작품 등록 → 공유 가능한 전시안. 파일 준비 여부를 함께 기록하고 초기 사용자 시험으로 목표 확정 |
| Correction Cost | 인식 후 벽·문·기둥 추가/삭제/이동 횟수와 소요 시간. 수동 작성 대비 보정 시간 50% 절감을 초기 검증 목표로 제안 |
| Placement Efficiency | 준비된 작품 10점을 지정 중심 높이·간격으로 배치. 소요 시간과 사용자 조작 수를 측정 |
| Share Completion | 별도 비로그인 세션에서 링크 열기·Scene 전환·작품 기본 정보 확인을 성공 |
| Recovery | 로컬 저장 완료된 명령은 새로고침·오프라인 후 복원, 클라우드 충돌 시 사본 보존 |

인식 품질 목표가 미달이면 출시 전에 지원 입력 조건 또는 기간을 재조정한다. 아름다운 3D 화면만으로 통과시키지 않는다.

## 10. 초기 착수 순서와 남은 결정 — 아래는 초기 계획 기록

현재 다음 작업은 M0-A1이며, 이 절의 초기 순서는 현재 우선순위가 아니다.

첫 2주에는 실제 도면·작품 자료와 기본 재질 프리셋을 준비하고 인식 결과의 수정 시간을 측정한다. 동시에 단위·벽 연결·작품 부착 데이터 모델을 구현해 5200mm 벽에 실제 치수의 작품 10점을 배치하는 최소 검증을 만든다. 이 결과를 기준으로 개발 기간과 지원 입력 조건을 확정한다.

현재 계획에 사용한 가정은 다음과 같다.

- 인력: 전담 개발자 2명과 일부 디자인·현장 검토 지원.
- 첫 고객: 사진·회화 전시를 준비하는 작가/큐레이터, 데스크톱 편집.
- 도면: 단층을 먼저 검증. 계단의 위치·평면 영역과 설치 제한 표시는 자동 인식 범위에 포함한다. 복잡한 천장·BIM 및 계단의 상세 3D 구조 자동 복원은 후속 범위다.
- 공유: 게시 스냅샷을 명시적으로 갱신. 내부 Note는 기본 비공개.
- Area Light: MVP에서 자체 그림자 없음. Spot/Sun 그림자와 조합.
- 인증 제공자와 인식 처리기 공급자는 1–2주 기술 검증에서 확정한다. 가격·계약은 아직 산정하거나 체결하지 않았다.
- 인프라 비용은 사용자 수보다 저장 원본 용량, 파생 이미지 처리, 인식 작업 수·시간, 출력 빈도를 먼저 측정해 월간 예산으로 환산한다.

계획에서 가장 먼저 확정할 것은 첫 출시 기한과 실제 투입 인력이다. 제품 개발의 첫 구현 대상은 공통 치수 모델과 2D 보정·벽면 배치이며, 자동 인식 실험은 같은 시점에 시작한다.

## 범위 보완 — 전시장 전체 구성 (2026-09-11 사용자 요구)

사용자는 바닥과 벽 두 면으로 보여 주는 단순 공간뿐 아니라 전시장 전체를 구현하는 경우도 지원하도록 요청했다. 전시장 전체 구성은 핵심 공간 편집 요구사항에 포함한다. 아래 상세 항목은 이를 위한 설계안이며, 모두 현재 구현된 기능을 의미하지 않는다.

### 공간 모델
- 프로젝트 아래 전시장, 층, 전시실/공간 영역을 구분한다. 단층 전체 전시장을 우선 구현하고 여러 층은 같은 모델에서 확장한다.
- 외벽과 내부벽/가벽, 공유벽, 바닥 외곽과 중정/구멍을 명시적으로 표현한다. 실마다 공유벽을 중복 생성하지 않는다.
- 문/창/출입구는 벽에 연결된 개구부로, 기둥은 독립 구조 요소로 관리한다. 벽 높이·두께와 개구부 치수는 실제 단위로 저장한다.
- 작품은 벽 ID뿐 아니라 벽의 어느 면에 설치됐는지 기록한다. 내부 가벽 양쪽 면의 전시를 지원한다.
- 도면의 평면만으로 알 수 없는 높이·층간 관계는 기본값/미확정 상태를 표시하고 사용자가 입력한다.

### 보기 및 편집
- 전체 조감도, 지붕/천장 숨김, 선택 공간 집중 보기, 실내 눈높이 탐색을 구분한다.
- 벽 자동 숨김은 보기 설정이다. 벽 삭제나 도면 구조 변경, 저장된 실제 전시장 형상에 영향을 주지 않는다.
- 전체 전시장에 맞춰 카메라를 자동 배치한다. 벽 두 면만 보이는 컷어웨이는 선택 가능한 보기 방식으로 유지한다.
- 객체 목록을 공간별로 탐색하고 다수의 벽·작품을 선택/잠금/숨김 처리할 수 있게 한다.

### 구현 순서 및 검증
1. 도면 원본 보존·확대·축척 검증을 먼저 보강한다.
2. 외곽/공간 영역과 벽을 분리하고 공유벽·T접합·바닥 구멍을 지원한다.
3. 개구부·기둥·벽 양면 작품 배치를 구현한다.
4. 전체 조감도와 실내 탐색, 공간별 선택/표시 기능을 연결한다.
5. 계단의 평면 위치·방향·설치 제한 영역을 자동 인식한다. 복수 층과 계단의 상세 3D 형상·층간 연결은 후속 확장으로 세부 범위를 정한다.

필수 검증 사례: 여러 전시실과 복도, 공유벽 하나, 양면 가벽, 출입구, 기둥, 중정이 있는 단층 전시장. 벽/바닥 중복이나 중정 채움이 없고, 작품이 지정한 면에 붙으며, 보기 전환·저장·재열기 뒤 구조가 유지돼야 한다. 실내 탐색의 충돌 처리는 별도 검증하며 단순 카메라 이동만으로 통행 가능성을 보장하지 않는다. 피난·법규 적합성 분석은 이 요구에 포함하지 않는다.

기존 200벽/500작품 한도와 렌더링 성능은 실제 전체 전시장 샘플로 평가한 뒤 조정한다. 한도 변경만으로 대규모 공간 지원을 완료했다고 보지 않는다.


## 자동 인식 범위 확정 — 구조·설비·설치 제한 (2026-09-11)

사용자는 수동 객체 추가가 아니라 **도면 입력 시 자동으로 인식하고 표시하는 범위**를 지정했다. 아래 항목을 핵심 자동 인식 목표로 포함한다. 현재 직선 후보 검출만으로 달성한 것으로 보지 않는다.

| 대상 | 자동 추출 및 표시 | 값/판정의 근거 |
|---|---|---|
| 벽 | 경로·길이·높이·두께, 어느 면에 설치할 수 있는지 | 치수 문자와 대상 벽 연결 우선. 보정된 축척·이중 선 간격으로 길이/두께 계산 가능. 높이는 입면/단면/표기에서 확인하며 없으면 미확인 |
| 출입구/문 | 위치·너비, 연결된 벽, 여닫이 방향·문 열림 영역 | 개구부·문 기호·명칭·범례를 함께 해석. 높이·문 방식이 불명확하면 미확인 |
| 에어컨 | 위치·외곽, 도면에 구분된 경우 벽걸이/천장형/바닥형 | AC·에어컨 등 문자와 설비 도면 범례/기호를 연결. 설치 높이·깊이·서비스 공간은 근거 없으면 미확인 |
| 소화전/소화설비 | 위치·표시명·접근을 확인할 영역 | 문자·범례·기호. 소화전과 소화기를 임의로 같은 종류로 확정하지 않음 |
| 계단 | 평면 영역·방향, 설치 제외 표시 | 단선·UP/DN·층표기·범례. 인접 복도 전체를 계단으로 판단하지 않음 |
| 기타 구조/설비 | 기둥·창·고정 설비와 확인이 필요한 미분류 설비 | 인식하지 못한 장애물을 버리지 않고 미분류 후보로 표시 |

### 인식 결과의 데이터와 검토
- 항목별 원본 파일·페이지·영역 좌표, 검출 박스/윤곽, 유형, 연결 벽/벽면, 원문 문자/범례 참조를 보관한다.
- 각 치수는 값·단위·근거(`명시된 치수`, `축척 계산`, `사용자 확인`, `미확인`)를 개별 보관한다. 벽 길이를 알아도 높이가 자동으로 확인된 것은 아니다.
- 인식 후보의 확신도와 사용자가 검토했는지 여부를 구분한다. 확신도 수치만으로 정확도나 설치 가능성을 보장하지 않는다.
- OCR 숫자만 읽는 데서 끝내지 않고 치수선/보조선의 양 끝과 연결해 어느 벽/개구부에 대한 값인지 확인한다. 총치수/부분치수의 모순을 표시한다.
- 위치가 확실하고 높이가 미확인인 설비는 2D 표시 및 3D의 미확인 마커로 유지한다. 임의 높이를 실측값처럼 채워 완전한 3D 설비로 표시하지 않는다.
- 원본에 표기가 없거나 읽지 못하면 `없음` 대신 `확인 필요`로 남긴다. 특히 미검출 소방설비가 없다고 추론하지 않는다.

### 설치 가능성 표시
1. **공간 점유 영역**: 계단·기둥·고정 설비 실체 등과 겹치는 영역을 표시한다.
2. **접근/작동을 검토할 영역**: 문 열림, 출입 동선, 소화전 접근, 에어컨 점검 영역은 객체 실체와 별도 윤곽으로 표시한다. 도면/시설 지침/사용자 확인으로 범위를 정하며 임의 거리로 확정하지 않는다.
3. **벽면의 설치 가능 구간**: 벽의 A/B면별로 문/창/설비가 차지하는 길이와 높이를 제외한 구간을 계산한다. 바닥 제한 영역을 전체 벽 높이에 무조건 적용하지 않는다. 천장형 에어컨을 바닥 전체 설치 금지로 취급하지 않는다.
4. **미확인 구간**: 높이/설비 깊이/접근 범위 부족 시 설치 가능을 확정하지 않고 검토 필요로 표시한다.
5. 평면도·벽면도·3D에서 같은 객체와 제한 근거를 선택해 확인한다. 작품/가벽이 확정된 장애물과 겹치면 충돌을 표시하고, 미확인 접근 영역은 검토 안내로 구분한다.

이는 전시 계획을 돕는 공간 판단이다. 시설 운영 정책과 관련 기준에 따른 최종 허용 여부를 도면 인식만으로 확정하는 기능은 아니다.

### 자동 인식 처리 순서
1. 원본 보존, 페이지 종류(평면/입면/설비/범례) 분류 및 평면 영역 연결.
2. 벡터/텍스트 추출과 스캔 OCR·시각 기호 인식을 병행. 선 후보 검출은 보조 입력으로 사용.
3. 치수-벽 연결, 문/설비/계단 기호와 범례 대조, 대상 영역·단위별 축척 검증.
4. 항목별 근거/미확인 값과 검토 화면 생성. 알려진 구조로 3D를 생성하고 미확인 항목 표시.
5. 객체 점유·문 작동·접근 영역 및 벽면별 설치 구간 계산, 사용자 보정과 저장 연동.

검증 정답에는 벽 치수뿐 아니라 출입구·에어컨·소화전/소화기·계단 위치, 미확인 높이, 설치 제한 근거와 영역을 포함한다. 객체별 누락/오검출과 치수-대상 연결 오류를 따로 측정한다. 총 후보 개수를 인식 성능으로 보고하지 않는다.
