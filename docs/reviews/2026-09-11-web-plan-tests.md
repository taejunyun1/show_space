# 웹 공개 도면 실입력 테스트

## 출처와 사례

2026-09-11에 공개 PDF를 테스트용으로 내려받았다. 공개 접근 가능함과 재배포 허용은 구분한다. 원본·렌더 이미지는 `/tmp/gonggan-real-plans`에 두고 제품 예제 배포물에는 포함하지 않았다.

| 파일 | 출처 | 분량 | 확인한 난점 |
|---|---|---:|---|
| japan-foundation.pdf | https://nd.jpf.go.jp/wp-content/uploads/2022/11/All_Drawing_Files.pdf | 50쪽, 10,123,285바이트 | 6쪽 전시장 작업 평면: 많은 치수·기호·기둥·가변 문, 13쪽 작은 글자 |
| nelson.pdf | https://nelsonmuseum.ca/wp-content/uploads/2022/11/Gallery-Floorplan-Specs.pdf | 1쪽, 673,180바이트 | 설명문과 평면 혼재, 피트/인치 치수, 비직각 외곽과 연결 공간 |
| jica-scan.pdf | https://openjicareport.jica.go.jp/pdf/10552867.pdf | 57쪽, 1,948,273바이트 | JBIG2 스캔, 텍스트 레이어 없음. 43쪽은 회전된 두 층의 평면이 한 장에 있음 |

## 발견 및 수정

1. **스캔 페이지 내용 누락**: 지원 리소스 경로 없는 PDF.js로 JICA 문서를 처리하면 JBig2 초기화 실패와 image decode 경고가 발생했다. WASM/CMap/표준 폰트를 앱과 함께 제공하고 경로를 설정했다. 치명적 파싱/렌더 오류는 부분 결과 대신 실패로 처리하도록 설정했다. 수정 후 Node 재검증에서 해당 디코더 경고가 없어졌고 브라우저 43쪽도 실제 도면이 표시됐다.
2. **이미지 도면 손실 압축**: 작품용 2048px WebP 경로를 분리했다. 이미지 도면은 최대 4096px PNG로 변환하며 작은 입력은 확대하지 않는다. 큰 원본을 축소했다면 안내한다. 원본 파일 영구 보존은 아직 미구현이다.
3. **세부 검토 부족**: PDF 2400/4800px 선택, 미리보기 픽셀 크기 확인과 스크롤, 평면도 100~1600% 확대/축소·전체 맞춤·이동 모드를 추가했다. PDF 저장 한도로 JPEG 변환이 필요한 경우 압축 안내를 표시한다.
4. **입력 품질 안내 없음**: 비어 있지 않은 PDF 텍스트 항목의 렌더 높이가 9px 미만인지 검사한다. 텍스트 레이어가 없거나 검사를 못 했을 때 별도 안내한다. 스캔 판정/문자 인식률을 단정하지 않는다. 이미지 짧은 변 800px 미만은 확인 권고용 휴리스틱이다.

## 검증 결과와 범위

- 108페이지 메타데이터/텍스트/그리기 연산 점검. 모든 페이지의 고해상도 시각 검수를 완료했다는 의미는 아니다.
- JICA 57페이지 썸네일 시트 렌더로 페이지를 탐색하고 43쪽을 브라우저에서 직접 확인했다.
- 일본국제교류기금 6쪽: 브라우저 기본 1696×2400, 고해상도 3393×4800 렌더, 배치 후 225% 확대 확인. 6쪽에는 비공백 텍스트 기준 9px 미만 경고 대상이 없었다. 공백 항목의 높이 0을 글자 크기로 세면 오탐하므로 제외했다.
- 일본국제교류기금 13쪽/14쪽: CLI 진단에서 각각 4개/1개의 비공백 항목이 9px 미만.
- Nelson PDF: 브라우저 미리보기 정상. 동일 도면을 247×320으로 축소한 **인위적 저해상도 변형**을 별도로 만들어 크기 유지·저해상도 안내를 확인했다. 원본 품질이 낮다는 주장과 구분한다.
- 벽 자동 인식이나 실제 치수 정확도를 테스트한 것은 아니다. 현재는 수동 벽 편집기다.

## 재현

원본을 위 URL에서 해당 파일명으로 `/tmp/gonggan-real-plans`에 내려받은 뒤 실행한다.

```sh
node scripts/check-real-plans.mjs /tmp/gonggan-real-plans
node scripts/scan-contact.mjs /tmp/gonggan-real-plans
npm test
npm run build
```

`real-plan-results.json`은 원문 텍스트를 제외한 페이지별 진단 기록이다. `scripts/sync-pdf-assets.mjs`는 설치된 PDF.js와 동일 버전의 지원 파일·라이선스를 public/pdfjs에 복사하며 postinstall에서 실행된다. PDF.js 옵션 근거: https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html

## 문자 기반 설비·치수 후보 인식 (2026-09-11)

- PDF 텍스트 좌표를 도면 픽셀 좌표로 변환하고, 텍스트가 없는 페이지·이미지는 브라우저의 한국어+영어 OCR로 읽는다. OCR은 로컬 모델을 사용하며 도면을 외부 API로 전송하지 않는다. 취소·90초 시간 제한·재인식을 제공한다.
- 출입구/문/에어컨/소화전/소화기/계단/기둥/단위가 있는 치수 표기를 후보로 분류한다. 단위 없는 숫자는 치수로 확정하지 않는다.
- 평면도에 표기 상자를 표시하고 종류 수정, 표기 확인, 오인식 제외를 지원한다. JSON/로컬 저장에 원문·상자·출처·검토 상태를 포함한다. 회전·자르기에 상자를 변환하며 잘린 문자는 제외한다.
- **상자는 문자 위치이며 설비 실체나 설치 금지 면적이 아니다.** 확인 상태 역시 문자 종류·위치 확인만 뜻한다. 문 기호/계단 범위/설비 점유 및 접근 영역, 벽과 치수 연결·높이/두께 추정, 벽 양면 설치 가능 구간 계산은 남아 있다.
- PDF에 일부 텍스트만 있고 본문이 스캔이면 자동 OCR이 생략될 수 있으므로 ‘문자 다시 읽기’를 사용할 수 있다. 이 동작은 현재 가져오기 미리보기의 문자 후보를 새 OCR 결과로 교체한다.
- 실제 Japan Foundation 도면 6페이지: PDF 텍스트 후보 9개(Up/Dn, Entrance, Sliding Folding Door, 2m wide Door, 치수 표기 등). 후보 수는 실제 설비 개수나 정확도가 아니다.
- 합성 영문 이미지: 7개 표기 추출, 확인/제외/평면도 반영/Undo 브라우저 검증. 합성 한국어 이미지(AppleGothic): 6개 표기 중 5개 추출, ‘출입구’ 누락. 한국어 OCR의 누락 가능성을 확인했으며 실제 저해상도·기호 전용 도면에 대한 정확도 검증은 아직 없다.
- 빌드 및 자동 테스트 100개 통과. 기존 사용자 도면은 테스트 후 복원했다.

## 숫자 인식 집중 개선 (2026-09-11)

사용자 결정: 설비 이름 OCR 개선은 후순위로 두고 숫자 인식 단계를 먼저 마무리한다.

- 단위 없는 숫자, H/T/W/L 표기, 전각 숫자, 연속 치수 숫자를 후보에 포함한다. 단위는 임의로 mm로 가정하지 않는다. 쉼표의 천 단위/소수 해석을 둘 다 보존하며 저점수 OCR과 여러 숫자를 별도 안내한다.
- 축척 1:100, A101 같은 번호, 날짜·레벨 표기 등은 숫자 판독기에서 제외한다. 단독 숫자는 페이지/실 번호일 수도 있어 검토 후보로만 남는다. O/0, I/1 등을 자동 치환하지 않는다.
- ‘숫자 정밀 다시 읽기’: 영문 모델과 최대 2배 확대·3600px 입력 사용. 문자 화이트리스트로 비숫자를 강제 변환하지 않는다. 새 숫자 후보로 교체하고 기존 비치수 설비 후보를 유지한다. 확대는 원본의 손실된 정보를 복원하지 않는다.
- 숫자 검토 화면에 해당 원본 부분을 확대 표시한다. ‘숫자 정정 저장’은 원문을 유지한 채 correctedText를 저장하며 검토 상태를 초기화한다. 저장/회전/자르기에서도 정정값을 보존한다.
- 브라우저 합성 이미지 검증: 3200, H=2800, 200 mm, 3,200, 1200 2400 3600의 5개 표기 인식. 1:100/A101 제외. 정밀 읽기 후에도 동일 표기 판독. 3,200 → 3200 mm 정정·확인·Undo 검증. 이는 실제 저해상도 도면 정확도 수치가 아니다.
- 실제 Japan Foundation 6쪽: 이전 9개에서 단위 없는 숫자 후보가 추가되어 총 53개 표기 후보. 증가 수는 정확도 개선율이나 실제 치수 수가 아니다. 원본 파일이나 사용자 작업은 변경하지 않았다.
- 빌드 성공, 자동 테스트 107개 통과. 숫자 단계는 이 범위에서 마무리한다.

다음 구현 단계: 검토한 숫자와 치수선/벽 후보의 연결. 단위·대상 벽·길이/높이/두께를 확인한 뒤 적용하며 현재는 자동 벽 치수 변경을 수행하지 않는다. 복잡한 기호 인식이나 설비 이름 OCR 개선으로 이번 숫자 단계의 범위를 확대하지 않는다.
